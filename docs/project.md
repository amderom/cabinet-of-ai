## Project compass

> Validated with the project's operator during Vibe Project. This is the
> decision filter for every feature: read it before any `/spec`. Change it
> only with the user's explicit agreement.

**Why** — Cabinet of AI shows that the ideas behind artificial intelligence are centuries old, and it does this by letting people play with them. It's a cabinet of curiosities of AI's historical prefigurations, each rebuilt as a playable object with vibe coding. It's also a research and AI portfolio, built to support a LinkedIn series and turn readers into followers.

**Principles**
1. **Play first, read second.** Every exhibit is touched before it's explained.
2. **Old ideas, 2026 craft.** The past lives in the objects, labels and inscriptions, never in the interface.
3. **Scholarship and parody side by side.** Each exhibit holds a serious essay and a start-up parody, and neither one undermines the other.
4. **Phone first.** Visitors arrive from LinkedIn, mostly on their phones. Desktop gets extras, but the phone gets the full experience.
5. **Every part is shareable.** Demo, essay and making-of each have their own link, so any post can point to the exact place it talks about.
6. **Show the making.** A short making-of shows how each object was built with AI. That's part of the portfolio.

**Not in scope (for now)**
- No admin interface or CMS: content is edited in code with AI agents.
- No accounts, comments or contact form: LinkedIn is the only channel.
- No analytics: LinkedIn statistics are enough.
- English only: the French version is parked for later.

## Tech Stack

> Validated with Context7 before project start (2026-11-09). Astro moved to 7.x on 2026-11-10 — see [ADR 001](./adr/001-astro-7.md).

### Frontend
- **Framework:** Astro 7.4.x (static output; requires Node 22.23.4+, even-numbered versions)
- **UI islands:** React 19.x
- **Language:** TypeScript 5.x
- **Content:** MDX via `@astrojs/mdx`, Astro content collections. Markdown/MDX is processed by Astro 7's default engine (Sätteri); fallback to the classic remark engine (`@astrojs/markdown-remark`) if an essay needs something Sätteri lacks
- **Styling:** Tailwind CSS 4 (added with `npx astro add tailwind`, official Vite plugin). Design tokens are defined as Tailwind theme variables (CSS custom properties); each exhibit sets its own accent variable. Hand-written CSS only for the cabinet and demo visuals that Tailwind can't express cleanly.
- **Page transitions:** Astro view transitions (`<ClientRouter />` from `astro:transitions`, `transition:name`, `transition:persist`)
- **Testing:** Vitest for demo logic (`npm run test`); browser checks via `playwright-cli` (see AGENTS.md)
- **Fonts:** self-hosted in the repo (never loaded from a third-party font CDN such as Google Fonts, so no visitor data leaves the site)

### Backend
None. Fully static site — no server, no API, no authentication.

### Database
None. Content lives in files in the repository.

### AI / External Services
None at runtime.

### Infrastructure
- **Platform:** Vercel, Hobby (free) tier — static deploy, no adapter needed
- **Version control:** GitHub (private repo for now)
- **Domain:** free `vercel.app` subdomain for the MVP (custom domain parked in IDEAS.md)
- **Monitoring:** none

### Approved third-party libraries
- `@astrojs/react@7` — React islands
- `@astrojs/mdx@8` — MDX content
- `tailwindcss@4` + `@tailwindcss/vite` — styling (installed via `astro add tailwind`)
- `gsap@3.15` + `@gsap/react` — animation; all plugins (ScrollTrigger, SplitText, Flip, Draggable…) are free, including commercial use
- `howler@2.2` — sound effects across the site (version to confirm at install; not listed by Context7)
- `tone@15.1` — generative music, loaded **only** inside demos that need it (first use: Glass Bead Game, post-MVP)
- `vitest@5` — unit tests
- `@astrojs/check` + `typescript@5` — type checking (`npm run check`), dev only

### Forbidden patterns
- No libraries released less than 6 months ago without explicit approval
- No heavy library loaded site-wide when only one page needs it (e.g. Tone.js loads only where used)
- No server-side features (API routes, SSR, databases) — the site stays static
- No CMS or admin interface (see Project compass)
- No analytics, tracking scripts or cookies

### Version policy
All versions above were verified via Context7 at project start, except Howler (not listed by Context7 — confirm the stable 2.2.x release at install).
Any upgrade must be re-validated via Context7 (or the official docs when Context7 lags) and documented as an ADR in `docs/adr/`.
Exception to the 6-month rule: Astro 7 (released 2026-06-22), approved by the operator — see ADR 001.

## Architecture

### Overview
A static Astro site. Pages are plain HTML by default; interactive parts (each exhibit's demo, the cabinet, the sound controls) are React islands that load only on the pages that use them. Exhibits are content entries (MDX + metadata), so adding an exhibit means adding a content entry and its own demo component, without touching the rest of the site.

### Domain Map

| Domain | Responsibility | Key Files/Folders |
|---|---|---|
| Content | Exhibit metadata (title, slug, accent colour, status open/sealed, order, credits), essays and making-of texts | `src/content/exhibits/<slug>/` |
| Pages & routing | Home, exhibit demo page, essay page, making-of page | `src/pages/` |
| Layouts & UI | Shared layout, typography, tokens, navigation, calls to action, link previews (Open Graph) | `src/layouts/`, `src/components/`, `src/styles/` |
| Demos | One self-contained React island per exhibit, including its parody framing | `src/demos/<slug>/` |
| Cabinet | Homepage cabinet: illustrated 2D cabinet, animated with GSAP (no 3D) | `src/cabinet/` |
| Sound | Sound preference (with sound / in silence), persistent mute toggle, sound-effect playback. The preference is kept in memory and `localStorage` only — never in cookies | `src/sound/` |
| Credits | Source, author and licence of every third-party asset, shown on each exhibit and in a site-level credits spot for cabinet assets | exhibit metadata (`credits`), `src/components/` |
| Static assets | Images, sounds, link-preview images | `public/` |

### Routes

| URL | Content |
|---|---|
| `/` | The cabinet (homepage) |
| `/exhibits/<slug>/` | Demo + parody |
| `/exhibits/<slug>/essay/` | Essay |
| `/exhibits/<slug>/making-of/` | Making-of |

Every URL has its own Open Graph title, description and preview image (LinkedIn link previews). Sealed exhibits have no public pages.

### Data Flow

```
Content entries (src/content/exhibits) → Astro pages (build time) → static HTML
                                       → cabinet drawers (open / sealed)
Visitor interaction → React island (demo / cabinet) → sound module (if sound is on)
```

### Dependency Rules

```
content → styles/tokens → components → layouts → pages
demos, cabinet → may import components, styles and sound; never each other
sound → depends on nothing else in the app
```
Each demo is self-contained: it never imports another demo.

### Key Architectural Decisions

| Decision | Rationale | Alternatives rejected |
|---|---|---|
| Astro, static output | Fast on phones; heavy code loads only where needed | Next.js (built for server apps, heavier), plain HTML/JS (messy as exhibits grow) |
| React for islands | Ecosystem agents handle most reliably | SvelteKit (less reliable agent output) |
| Tailwind CSS 4 for styling | Agents apply one shared scale (spacing, type, colour) consistently across exhibits; theme variables support per-exhibit accents | Plain hand-written CSS (more drift between exhibits over time) |
| Content in MDX files, no CMS | The author edits through AI agents; no admin to maintain | Headless CMS |
| Illustrated 2D cabinet, no 3D | Phone-first principle; 3D lags on weaker phones and was the riskiest piece of the MVP | 3D cabinet with React Three Fiber (dropped by the operator) |
| Howler site-wide, Tone.js per demo | Howler is small; Tone.js is heavy and only needed for musical demos | Tone.js everywhere |
| Sound opt-in after first gesture | Browsers block autoplay; visitors are often in public or at work | Autoplay |

> Significant architectural changes after project start should be captured as
> ADRs in `docs/adr/` via the `documentation-and-adrs` skill.

### Anti-Patterns
- No demo-specific code in shared layouts or components
- No hard-coded exhibit lists: the cabinet and navigation read the content collection
- No sound that plays before the visitor's first gesture, and no sound without a visible mute control
- No essential information delivered only through sound
- No third-party asset without its source and licence recorded (see AGENTS.md → Assets and credits)

## Design references

- **Design folder:** `design/` at project root (always exists, may be empty). Single home for design: visual assets in freeform subfolders, plus the `DESIGN.md` spec if one is added later.
- **Design system specification:** none yet. If a `design/DESIGN.md` is added (getdesign.md convention), agents read it before generating UI.

**Visual direction agreed during Vibe Project:**
- Dark background, contemporary interface. Vintage appears only in objects, labels and inscriptions — never as ornament on the interface. A period typeface (e.g. an 18th-century print face) is reserved for labels and inscriptions on objects, not for interface text.
- One accent colour per exhibit, inspired by the object, pushed to a saturated, modern colour (neon on near-black). The contrast is the point: vintage content, unmistakably 2026 presentation.
- The homepage looks like an actual cabinet (a piece of furniture). No exhibit is the entry point.
- Engravings are the main illustration source, from free-to-use, public-domain collections.
- Motion: light CSS animations, page transitions, GSAP sequences. No 3D for now.
- Sound: optional enhancement, never required to understand anything.
- The operator's own photos and drawings shared during Vibe Project were for mood only and must **not** be used on the site.

**Reference websites** (for feel, not to copy):
- redassociates.com — restrained editorial serif typography (model for the essay layer)
- costarastrology.com — phone-first product feel, white space, serif wordmark
- grail-app.com — a single object as the hero, playful animation
- deepbook-v2-wip.webflow.io — black screen, generative animated lines, one saturated accent
- theothersideoftruth.com — operator reference, not yet reviewed in detail

When working on UI-related features, always consult `design/` (and `design/DESIGN.md` if present) in addition to the standard foundation files.

## Deployment Workflow

> This is the immutable deployment workflow for this project.
> Any deviation must be discussed and documented as an ADR.

### Setup
- **Repository:** GitHub (operator's account), **private** for now. May be made public later (the making-of is part of the portfolio) — the operator decides.
- **Platform:** Vercel (Hobby tier), connected to the GitHub repository

### Strategy

`main` is the stable and deployable branch. Day-to-day work happens on
short-lived branches merged into `main` via PR.

**Branch flow:**
- `main` → auto-deploy to production on Vercel
- `feature/*` → new user-facing feature or project phase
- `fix/*` → bug fix
- `docs/*` → documentation-only change
- `chore/*` → maintenance/config change
- `refactor/*` → behavior-preserving code simplification

All task branches are merged into `main` via PR after review and checks. Every PR gets a Vercel preview URL; check it on a phone before merging.

**Environment variables:**
- None. The site uses no secrets.
- Never commit `.env` files.

**Database migrations:**
- Not applicable (no database).

**Rollback:**
- Fastest: promote a previous deployment from the Vercel dashboard
- Then: `git revert <commit>` on a `fix/*` branch → PR into `main` (never push directly to `main`)

**URLs:**

| Environment | URL |
|---|---|
| Local | `http://localhost:4321` |
| Active deployed environment | ASSUMPTION: `https://cabinet-of-ai.vercel.app` — confirm after first deploy |

**Never:**
- Commit or push directly to `main` unless explicitly requested by the user
- Merge a task branch without review/checks
- `git push origin main --force`

## Constraints

### Security level
- [ ] Prototype — internal, no sensitive data
- [ ] Internal production — company data, no PII
- [x] Production — user data, full OWASP baseline
- [ ] High security — financial / medical / legal

> Note: this is a public production site, but it collects **no** user data — no forms, accounts, cookies, analytics or third-party font/CDN calls. The baseline applies to what the site serves (security headers, dependencies, assets).

### Compliance
- GDPR: no personal data is collected or processed. Any future feature that collects data needs explicit approval and an ADR.
- Data retention: not applicable (no data collected).
- Asset licences: every third-party image, sound or 3D model must be free to use (public domain, CC0, or a licence compatible with a public portfolio), with source and licence recorded.
